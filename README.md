# Food Delivery Insights: ETL, Analysis and Tableau Dashboard

An end-to-end data analytics project modelled on a food-delivery platform like Zomato or Swiggy. It takes messy raw order and restaurant data, cleans it with logged quality rules, loads it into a SQL star-schema warehouse, produces statistical analysis and charts, and feeds an interactive Tableau city explorer.

## Business questions

- Which cities drive the most revenue, and where are cancellations highest?
- How much does delivery time hurt customer ratings?
- Does restaurant price predict customer rating?
- Which cuisines dominate each city?

## Key findings

Full output is in [reports/key_findings.md](reports/key_findings.md).

- Ratings fall from **4.84** for deliveries under 20 minutes to **3.60** for deliveries over 45 minutes.
- Mumbai has the highest net revenue (34 lakh) and the highest cancellation rate (7.4%).
- Price and rating are essentially uncorrelated (r = -0.01): expensive restaurants are not rated higher.
- Cafes are the most common cuisine, and Ahmedabad has the highest share of cafes (39% of its restaurants).

> The data is synthetic, generated by `generate_raw.py` with deliberate quality issues. The findings reflect the generator's assumptions, not real market behaviour. See [Using real data](#using-real-data).

## Tech stack

| Layer | Tools | Used for |

| Language | Python 3.13 | Everything |

| Warehouse | SQLite | Star schema: `fact_orders`, `dim_restaurant`, `dim_date`, `bridge_restaurant_cuisine`, KPI view |

## Architecture

```
generate_raw.py  ->  data/raw/*.csv
                          |
                    etl/run.py  (extract -> transform -> load)
                     /                 \
   data/processed/food_delivery.db    tableau/data/*.csv
          |                                  |
   analysis/insights.py                 Tableau dashboard
          |
   reports/figures/*.png, reports/key_findings.md
```

The warehouse is the single source of truth. Charts query SQL directly, and Tableau reads the flat CSV exports.

## How to run

Requires Python 3.10 or newer.

```bash
# 1. Create and activate a virtual environment
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate

# 2. Install dependencies
pip install -r requirements.txt

# 3. Generate the raw data (skip this if you have a real export in data/raw/)
python generate_raw.py

# 4. Clean the data, load the warehouse, and export the Tableau files
python -m etl.run

# 5. Build the charts and key findings
python -m analysis.insights

# 6. Run the tests
python -m pytest -q
```

Expected output from step 4 ends with a quality report, for example `"orders_clean": 60000`. Step 6 should report all tests passing.

Then open `tableau/data/` in Tableau and follow [tableau/TABLEAU_GUIDE.md](tableau/TABLEAU_GUIDE.md).

Run the scripts from the project root. The `python -m` form is needed so the `etl` and `analysis` packages import correctly.

## Data-quality issues handled

Every rule that drops or fixes rows is counted and written to `data/processed/quality_report.json` on each run.

| Issue | Rule | Count in the sample |
|---|---|---|
| Inconsistent city names (`bangalore`, `MUMBAI `, `New Delhi`) | Normalised to canonical names | All mapped, 0 unmapped |
| Price strings (`₹1,200`, `Rs. 850`) | Parsed to numbers with a regex | 12 missing, filled with city median |
| Multi-value cuisine field (`"Cafe, North Indian, cafe"`) | Exploded into a bridge table, trimmed and de-duplicated | 796 restaurant-cuisine pairs |
| Duplicate orders | Removed on `order_id` | 400 |
| Impossible delivery times (-1 and 999 minutes) | Set to NULL and excluded from timing metrics | 215 |
| Orders for unknown restaurants | Dropped and counted | 0 |
| Missing ratings | Kept, not imputed, and excluded from rating averages | 3,000 |

## Challenges faced

These are the real problems I hit while building the project, and how I solved them.

**1. A price parser that silently returned wrong numbers.**
The first version of `parse_money` kept every digit and dot. The string `"Rs. 850"` contains a dot after "Rs", so it became `.850`, which is 0.85. This would have corrupted the price tiers without raising an error. A unit test caught it. The fix uses a regex that extracts the first number, so the dot in "Rs." is ignored.

**2. A median fill that had nothing to fill from.**
Missing prices are filled with the city median. My first test fixture had only one restaurant per city, so when that restaurant's price was missing the median was NaN. The test failed for a data reason, not a code reason. I added a second restaurant to the fixture so the city has a real median.

**3. Chart x-axis labels that were unreadable.**
The monthly revenue chart first printed full timestamps that overlapped into an unreadable block. Setting a month locator showed only "Jan", because the axis was still being treated as categorical. The root cause was that SQLite returns dates as text, so seaborn plotted them as categories. The fix converts the month column to a real datetime when it is loaded from the database, and then sets explicit tick labels.

**4. A cuisine field that the first version did not really handle.**
The original pipeline kept only the first cuisine in each restaurant's list. That made cuisine popularity impossible to measure accurately. I added a bridge table with one row per restaurant per cuisine. The bridge table needed trimming and case-normalising, because `"Cafe"` and `"cafe"` were being counted as two cuisines.

**5. Keeping the Tableau output and the warehouse in sync.**
Tableau needs flat CSVs, while the analysis needs the star schema. Both are written from the same cleaned DataFrames in one pipeline run, so they cannot drift apart. Adding new fields such as latitude and longitude meant updating both the warehouse load and the export, which I tested by rerunning the whole pipeline.

**6. Checking my own written claims against the data.**
While writing the Tableau guide I wrote that Ahmedabad and Chennai both lead on cafe density. The heatmap showed Chennai at 24%, well behind Ahmedabad at 39%. I corrected the claim to name only Ahmedabad. Every number in this README was checked against the generated outputs.

**7. Environment setup.**
The system Python did not have matplotlib installed, so the first run failed. I ran everything through the project's virtual environment and listed every dependency in `requirements.txt`.

**8. No real data available.**
Real Zomato or Swiggy data would be the strongest version of this project, but downloading it needs a Kaggle account. I used a synthetic generator with deliberate quality issues instead. That lets the cleaning logic be tested against known faults, and it means the findings should be presented as a demonstration.

## Using real data

Replace `data/raw/restaurants.csv` and `data/raw/orders.csv` with a real export that uses the same column names. If the names differ, map them in `extract()` in [etl/run.py](etl/run.py). The cleaning rules in `etl/transform.py` will then run on the real data. Check the quality report afterwards, because real data will likely trigger rules the synthetic data never did.

## Limitations and next steps

- Data is synthetic, so the findings are illustrative.
- Restaurant-level ratings are averages of order-level ratings, with no weighting by order count.
- The SQLite warehouse is a single file. A production version would use PostgreSQL or a cloud warehouse.
- Possible extensions: a time-series forecast of demand, a cancellation-prediction model, and a Streamlit app.
